8: A=1. OBJECTIVES
9: A=• Reorganize and standardize the in-game flow architecture to address inconsistencies in the current implementation.
10: A=• Eliminate common logic bugs caused by flow inconsistency and UI bouncing tricks (rapid clicking, back-and-forth navigation, repeated actions).
11: A=• Ensure data state and UI state remain synchronized at all times.
12: A=• Establish a clear architectural foundation that:
      • Separates UI rendering from game logic
      • Centralizes flow control and validation
      • Improves maintainability, debuggability, and scalability
15: A=2. BACKGROUND
16: A=Current Issues
17: A=The current in-game flow | C=• Is implemented without a unified architectural pattern
• Has business logic:
     • Scattered across UI components, gameplay scripts, and services
     • Sometimes triggered directly from UI elements without centralized validation
18: A=As a result | C=• UI and data states can easily become out of sync
• Rapid player interactions (bouncing, spamming, fast navigation) can:
     • Trigger invalid or duplicated logic calls
     • Update data in an unintended order
• Bugs are often:
     • Hard to reproduce
     • Difficult to trace to their root cause
20: A=Root Cause Analysis
21: A=The core problems stem from | C=• Lack of a single authority responsible for controlling the flow
• UI components that:
     • Both display information and make logic decisions
     • Directly manipulate game data or states
• Absence of:
     • State validation before executing actions
     • A mechanism to serialize or lock critical flows

29: A=No | B=Step | D=Explain
30: A=[1] | B=Input on UI | D=In this step, we use two files: CustomUIUtils (to route button events) and HudXXX (to handle UI updates).
At this stage, there is no data-processing or game logic involved; the responsibility is strictly limited to UI presentation and interaction handling.

For UI flows that involve transactions (such as Swap Pets, Fuse Pets, etc.), the UI layer only stores display-related information required to build a Request.
The actual request is created and sent only when the player confirms the transaction.
31: A=[2] | B=Call RequestAction() | D=At this step, when the PLAYER confirms a transaction, the UI layer creates a Request using the parameters stored in the HudXXX file.
This request is then sent to the VALIDATION GATE.

Within the VALIDATION GATE, the system always performs the following checks in order:
      1. Validate the current state of the Player and/or Pet, if the action is state-dependent.
      2. Re-validate the request data against the current authoritative data, to prevent cases where the UI state differs from the actual game data.
      3. Validate action-specific rules, ensuring the request satisfies all constraints required for the specific action.

The system does not trust the UI; all requests must be verified to ensure consistency and correctness before any further processing.
32: A=[2.1] | B=Notify Error | D=In case validation fails, the VALIDATION GATE will notify an error back to the UI layer, and the request will be terminated without proceeding to execution.
33: A=[2.2] | B=Call DoAction() | D=If the validation passes, the VALIDATION GATE forwards the request to the ACTION MANAGER for logic execution.

Depending on the type of action, the Action Manager may be:
• an XXXManager at the global entity level, or
• a PlayerXXX component within the Player entity,
based on where the logic is most appropriately handled.
34: A=[3] & [4] | B=UpdateData() & Return UpdateStatus | D=At these steps, data updates may occur on either normal data (data that is persisted when the player quits) or core data (data that is updated in real time).

To ensure proper synchronization, all data update actions must return a status code indicating whether the update was completed successfully.
If the action fails or returns an invalid status, a rollback mechanism must be triggered to prevent any unintended impact on the user’s data.
35: A=[5] | B=Refresh UI | D=At this step, after the transaction is completed and the player data has been successfully updated, the UI must be refreshed to reflect the current authoritative data state.
37: A=How the New System Addresses Current Issues
38: A=Issues | D=How the New System Fixes It
39: A=UI–Data Desynchronization | D=• UI only prepares and forwards requests; it never mutates data.
• The Validation Gate re-validates all request data against the current authoritative data.
• The system explicitly does not trust the UI, ensuring that only valid and up-to-date data is processed.
40: A=Bouncing / Rapid Input Exploits | D=• All UI actions must pass through a single entry point (Validation Gate → Action Manager).
• The system can:
      • Reject repeated or invalid requests
      • Lock the flow while a transaction is being processed
• Invalid actions are ignored or rejected before execution.
41: A=Invalid Transactions | D=• Validation is performed in layers:
      • Player/Pet state validation
      • Request–data consistency validation
      • Action-specific rule validation
• Transactions only proceed if all validation layers pass.
42: A=Partial Data Updates & Data Corruption | D=• All data-modifying actions must return a status code.
• If any step fails:
      • The transaction is considered unsuccessful
      • A rollback is triggered to restore previous data
• This applies to both normal data and core data.
43: A=UI Not Reflecting Final Data State | D=• UI refresh is triggered only after data update success is confirmed.
• UI is refreshed using the current authoritative data, not cached UI state.
